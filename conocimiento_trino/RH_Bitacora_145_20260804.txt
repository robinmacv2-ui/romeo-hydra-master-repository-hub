   - Capturar y registrar en una colección de Firestore llamada `interacciones` cada acción relevante del usuario (ej. clics en botones clave, navegación entre secciones, consultas o despliegue de bloques).

   - Diseñar una sección de visualización limpia (estilo consola de auditoría minimalista con Tailwind CSS) donde se pueda ver en tiempo real:

     * Desglose de visitas por tipo (Usuarios Google vs. Invitados).
     * Tabla o lista de interacciones recientes con su respectiva marca de tiempo e identidad.
5. Seguridad (Reglas de Firestore):
   - Asegurar que las reglas de seguridad de Firestore permitan la escritura de visitas e interacciones para cualquier usuario autenticado (incluyendo anónimos), pero restrinjan la modificación o borrado de registros para mantener la integridad de la auditoría.

### 🛠️ Qué significa este error
En el log de tu consola se aprecia claramente el problema: **Firestore getLedgerBlocks timed out or failed**. Esto ocurre cuando una función asíncrona intenta consultar la base de datos en la nube, pero la conexión o la respuesta tardan más de lo esperado, provocando un tiempo de espera agotado (*timeout*).
Dado que tu aplicación ya cuenta con un sistema de respaldo ("*Returning local...*"), el objetivo principal es asegurar que ese código asíncrono maneje el fallo de manera limpia sin congelar la interfaz ni arrojar errores críticos.
### 🔧 Cómo corregir el código asíncrono
Para solucionar y blindar este tipo de llamadas, debes envolver la operación en un bloque **try...catch** y configurar explícitamente el manejo de la caché local de Firestore.
Puedes estructurar tu función de la siguiente manera:
```javascript
async function getLedgerBlocks() {
  try {
    // 1. Intentar la consulta normal al servidor
    const snapshot = await db.collection('ledgerBlocks').get({ source: 'server' });
    const blocks = snapshot.docs.map(doc => doc.data());
    return blocks;
  } catch (error) {
    console.warn("Firestore timeout o error de red detectado. Cambiando a respaldo local...", error.message);
    try {
      // 2. Respaldo: Forzar la lectura desde la caché local si el servidor falla
      const cachedSnapshot = await db.collection('ledgerBlocks').get({ source: 'cache' });
      return cachedSnapshot.docs.map(doc => doc.data());
    } catch (cacheError) {
      console.error("Error crítico: No se pudieron obtener datos ni del servidor ni de la caché.", cacheError);
      // 3. Retornar un valor por defecto seguro (ej. arreglo vacío) para evitar que la app se rompa
      return [];
    }
  }
}
```
### 📋 Claves para revisar en tu implementación
 * **Uso obligatorio de try...catch:** Toda operación con await debe estar protegida para capturar interrupciones de red sin crashear el sistema.
 * **Estrategia de respaldo:** Asegúrate de que cuando ocurra el timeout, la función devuelva una estructura válida (como un arreglo vacío [] o un objeto por defecto) en lugar de un valor nulo (undefined), lo cual evitaría errores posteriores al renderizar la interfaz.
 * **Control de conectividad:** Verifica si estás probando en un entorno local (como un emulador) o con una conexión intermitente, ya que los tiempos de respuesta de Firestore pueden ajustarse automáticamente según la estabilidad de la red.
